# Coding Agent 教学轨迹：登录返回 500

> [← 课次入口](../README.md) · 上一篇：[三种执行方式的伪代码](pseudocode.md) · 下一篇：[练习题](../practice/exercises.md)

这是一个假设的教学轨迹，用来展示如何把一次修复任务写成“行动 → 观察 → 下一步”。仓库、文件内容和测试输出为讲解构造，不是实际执行日志。

## 任务与边界

- **Goal**：修复登录接口返回 500 的问题，让正常登录路径恢复，并避免无关改动。
- **环境**：一个假设的代码仓库，包含 `auth.py`、`database.py`、`routes.py` 和 `tests/`。
- **可用行动**：列目录、读文件、运行测试、编辑文件。
- **停止条件**：测试通过只是信号之一；还要核对目标、改动范围和失败路径。

## 五步轨迹

| 步骤 | 行动（可观察） | 观察（反馈） | 下一步依据 |
| --- | --- | --- | --- |
| 1 | `list_files()` | `auth.py`、`database.py`、`routes.py`、`tests/` | 先定位登录相关代码，读取 `auth.py` |
| 2 | `read_file("auth.py")` | `login()` 读取 `password_hash` 字段，错误处理很少 | 静态阅读不足以确认失败原因，运行测试 |
| 3 | `run_tests()` | `FAILED test_login`，`KeyError: password_hash` | 错误指向字段不一致；准备最小修复并用测试验证 |
| 4 | `edit_file("auth.py")` | 补丁已应用（假设） | 用测试验证改动 |
| 5 | `run_tests()` | `12 passed` | 测试通过；还需要核对目标、改动范围和覆盖 |

每一步都可以写成“行动 → 观察 → 下一步”，而不是只记录一句“模型认为……”。这样复盘时能区分：哪一步是实际执行，哪一步是模型的建议，哪一步的观察支持了下一步判断。

在这个轨迹里，状态至少保存了目标、已读文件、测试输出和已应用的补丁。如果没有状态，agent 可能在第五步之后重复读取同一个文件，或忘记最初的 500 错误。

## 测试通过之后

`12 passed` 是重要证据，但不等于“修复任务已充分完成”。收尾前还要：

- **对照 goal**：登录是否真的从 500 变成成功响应？错误分支是否也符合预期？
- **检查 diff**：改动是否只触及 `password_hash` 相关逻辑，有没有顺手改动无关代码？
- **检查覆盖**：现有测试是否覆盖了原始失败路径？`12 passed` 可能没有覆盖真实触发条件。
- **检查根因**：字段不一致是代码问题、数据迁移问题，还是两者都有？
- **记录限制**：如果无法复现原始 500、无法运行完整测试或缺少环境，应报告这些限制，而不是宣布完成。

这也是 agent loop 的停止条件问题：模型可以提议“完成”，系统可以用可验证结果、测试或权限策略决定是否接受；人工复核是可选策略，不是所有 agent 系统都必须。测试通过只说明当前测试集没有失败，不自动证明任务目标已经满足。
